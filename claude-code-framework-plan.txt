# ============================================================
# CONTEXT
# ============================================================

We're building a reusable, stack-agnostic framework for AI-driven
software development with a CLEAR OWNERSHIP CHAIN.

CORE PHILOSOPHY:
- Ownership chain: Every stage has ONE owner (Product, Tech, or AI)
- Ticket movement = permission: AI only works when humans move tickets
  into AI columns
- GitHub is the system of record: ALL decisions logged on tickets.
  Connects to meeting notes, Slack, meeting-notes tools later
- Ask, don't assume: Every agent asks questions on GitHub when unclear
- Stack-agnostic: Same process, different stack.yml per project

REPO STRATEGY:
  2 repos per project (api, web) — no separate docs repo
  Use GitHub built-in features: Issues, Wiki, Releases, Discussions
  PRD = GitHub Issue (issue description IS the PRD)
  FRD = Separate GitHub Issue (linked to PRD, moves on Kanban)
  Execution Plan = Sub-tasks under FRD issue
  Decisions/Progress = Comments on relevant tickets


# ============================================================
# THE KANBAN BOARD (11 Columns)
# ============================================================

PRD lives in GitHub Wiki (living document, not a task).
FRD enters the Kanban board — this is where execution begins.

COLUMN                    OWNER      ENTERS BY         EXITS BY           AI ACTIVE?
──────────────────────    ─────      ──────────        ──────────         ──────────
1. FRD Draft              Product    Product creates    Product moves      ASSIST ONLY
2. FRD Tech Plan Review   AI         Product moves      AI moves           YES (generates exec plan)
3. Tech Plan Approved     Tech       AI moves           Tech moves         NO (waiting)
4. AI Development         AI         Tech moves         AI moves           YES (builds code)
5. Code Review            Tech       AI moves           Tech moves         NO (waiting)
6. Staging Ready          AI         Tech moves         AI moves           YES (deploys staging)
7. Staging Review         Product    AI moves           Product moves      NO (waiting)
8. Rework                 AI         Product moves      AI moves           YES (applies changes)
9. Ready for Production   Tech       Product moves      Tech moves         NO (tech deploys)
10. Done                  —          Tech moves         —                  NO

SPECIAL:
🚨 Hotfix               Tech/AI    Tech creates        Tech moves         YES (bypasses to AI Dev)

PRD LIFECYCLE (separate from Kanban):
  1. AI drafts PRD → pushes to GitHub Wiki
  2. Product reviews/edits directly on Wiki (version history = audit trail)
  3. Product creates FRD issue → links to Wiki PRD URL → FRD enters Kanban
  4. As features ship, AI updates PRD wiki page with actuals


# ============================================================
# THE RULE: TICKET MOVEMENT = PERMISSION
# ============================================================

AI CANNOT move a ticket INTO an AI-active column.
Only HUMANS can give AI permission to work by moving tickets into AI columns.

AI CAN move a ticket OUT of an AI-active column into a human-review column.
This is the handoff — "I'm done, your turn."

INVALID AI MOVES (AI must NEVER do):
  ✗ Anything → FRD Draft (only Product)
  ✗ Anything → Tech Plan Approved (only Tech)
  ✗ Anything → AI Development (only Tech)
  ✗ Anything → Staging Review → Ready for Production (only Product)
  ✗ Anything → Done (only Tech)

VALID AI MOVES:
  ✓ FRD Tech Plan Review → Tech Plan Approved (exec plan done)
  ✓ AI Development → Code Review (code done, PR ready)
  ✓ Staging Ready → Staging Review (staging deployed)
  ✓ Rework → Staging Review (rework applied)
  ✓ Rework → Code Review


# ============================================================
# STAGE-BY-STAGE DETAIL
# ============================================================

## STAGE 1: PRD DRAFT
Owner: AI (generates) or Product (writes directly)
Column: 📋 PRD Draft

Two entry points:
- Path A: Product creates issue with brief description → AI generates full PRD
- Path B: AI identifies need from codebase → AI creates issue + PRD
- Path C: Product creates issue with complete PRD already written

AI (@prd-writer) behavior:
1. Reads issue description + Figma (if linked)
2. Reads existing codebase for context
3. Generates PRD using PRD-TEMPLATE.md
4. Posts PRD as comment on the issue
5. Lists open questions
6. DOES NOT move the ticket — waits for Product

What gets logged on the ticket:
- The full PRD
- Open questions
- Figma screen descriptions
- Existing feature references


## STAGE 2: PRD APPROVED
Owner: Product
Column: ✅ PRD Approved

Product reviews PRD, comments with changes.
AI updates PRD based on comments.
When Product is satisfied → Product moves to "FRD Draft"

What gets logged:
- Product feedback comments
- AI's PRD revisions
- Final "PRD Approved" confirmation from Product


## STAGE 3: FRD DRAFT
Owner: Product (AI assists ONLY when asked)
Column: 📝 FRD Draft

Product writes the FRD — they decide WHAT gets built and the scope.
Three modes:
- Product writes FRD fully themselves
- Product gives pointers → AI structures into FRD format
- Mix: Product writes some sections, asks AI to fill gaps

AI (@frd-assistant) is PASSIVE — only responds when Product asks.
AI does NOT auto-generate the FRD.

When Product is done → Product moves to "FRD Tech Plan Review"

What gets logged:
- The FRD (by Product)
- Any AI assistance requests and responses
- Product's scope decisions


## STAGE 4: FRD TECH PLAN REVIEW
Owner: AI
Column: 🤖 FRD Tech Plan Review

AI picks up the ticket. This is where AI THINKS.

AI (@execution-planner) reads:
- The approved PRD
- The FRD from Product
- The codebase (all repos)
- stack.yml for tech stack
- Figma designs

AI generates the EXECUTION PLAN:
- Exact files to create/modify (with paths)
- Database model changes + migration strategy
- API contract (endpoints, request/response shapes)
- Celery task definitions
- Frontend component breakdown (from Figma)
- State management decisions
- Test plan with specific test cases
- Risk assessment
- Cross-repo coordination plan
- Deployment considerations
- Estimated sub-issues breakdown
- Feature flag definitions

AI posts execution plan on the ticket.
AI assigns ticket to tech lead / relevant engineer.
AI moves ticket to "Tech Plan Approved" column.

What gets logged:
- The complete execution plan
- Any questions AI has for tech team
- Risk flags


## STAGE 5: TECH PLAN APPROVED
Owner: Tech Team
Column: 🔧 Tech Plan Approved

Tech reviews execution plan and adds:
- DO's: "Use existing PaymentService", "Follow pattern in apps/billing/"
- DON'T's: "Don't modify auth middleware", "Don't add new Django apps"
- Constraints: "Max 2 new tables", "Must be backward compatible"
- Flags: "This migration will lock users table for ~5min"
- Architecture: "Use signals not direct calls"

When satisfied → Tech moves to "AI Development"
THIS IS EXPLICIT PERMISSION FOR AI TO WRITE CODE.

What gets logged:
- Tech team's DO's and DON'T's
- Architecture guidance
- Risk acknowledgments
- Reviewer name (they review code in Stage 7)


## STAGE 6: AI DEVELOPMENT
Owner: AI
Column: 💻 AI Development

AI reads everything accumulated:
- PRD (what, from Product)
- FRD (how, from Product)
- Execution Plan (how, from AI)
- Tech DO's/DON'T's (constraints, from Tech)

AI builds using specialized sub-agents:
- @model-builder → Django models + migrations
- @api-builder → DRF endpoints
- @task-builder → Celery tasks
- @design-interpreter → Figma → component mapping
- @component-builder → React/RN components
- @screen-builder → Pages/screens
- @state-architect → State management
- @api-client-gen → TypeScript API client
- @test-writer / @test-writer-fe → Tests

AI creates PR(s) linking to the ticket.
AI assigns to SAME person who did tech review (Stage 5).
AI moves ticket to "Code Review".

IF AI hits ambiguity during development:
- Comments on ticket with specific question
- DOES NOT move the ticket back
- Continues what it can, waits for answer on blocking items
- Tech answers async on the thread

What gets logged:
- "Starting development" comment
- Progress milestones
- Questions during development
- PR links with summary
- Test results + coverage


## STAGE 7: CODE REVIEW
Owner: Tech Team
Column: 👀 Code Review

The developer from Stage 5 reviews:
- Pulls code locally
- Runs it
- Reviews PR(s)
- Tests edge cases
- Pushes fixes to PR branch

When ready → Tech moves to "Staging Ready"

What gets logged:
- Code review comments (GitHub PR review)
- Fixes pushed by tech
- "Approved" or "Changes Requested" on PR


## STAGE 8: STAGING DEPLOY
Owner: AI
Column: 🧪 Staging Ready

AI (@staging-deployer) handles:
1. Documents exact staging deployment steps
2. Runs/assists staging deployment
3. Runs smoke tests + E2E tests on staging
4. Generates PRODUCTION DEPLOYMENT CHECKLIST:
   - Migration commands
   - Environment variables
   - Feature flags to enable
   - CDN/cache steps
   - Health verification
   - ROLLBACK PLAN (exact steps to undo)
5. Updates API docs + changelog
6. Posts checklist on ticket
7. Assigns to Product team member
8. Moves ticket to "Staging Review"

What gets logged:
- Staging deployment steps (executed)
- Smoke test + E2E results
- Production deployment checklist
- Rollback plan
- API doc updates
- Changelog entry


## STAGE 9: STAGING REVIEW
Owner: Product
Column: 🎭 Staging Review

Product tests feature on staging against acceptance criteria.

If GOOD → Product moves to "Ready for Production", assigns to Tech
If CHANGES NEEDED → Product comments with feedback, moves to "Rework"

What gets logged:
- Product's testing notes
- Acceptance criteria check (pass/fail)
- Change requests (with specifics)
- Screenshots/recordings of issues


## STAGE 10: REWORK
Owner: AI
Column: 🔄 Rework

AI (@rework-planner) picks up:
1. Reads Product's change feedback
2. Assesses scope: tweak or significant change?
3. If significant → updates execution plan, may need Tech review
4. If tweak → makes changes directly
5. Updates PR(s)
6. Moves ticket back to "Code Review" (Stage 7)

Loop: Rework → Code Review → Staging → Product Review
Until Product approves.

What gets logged:
- AI's rework assessment
- Changes made
- Updated PR


## STAGE 11: READY FOR PRODUCTION
Owner: Tech (with AI assistance)
Column: 🚀 Ready for Production

Tech deploys using AI's checklist from Stage 8.
AI assists with commands, monitoring, rollback.
Tech does the actual deploy — AI does NOT have prod access.

When deployed → Tech moves to "Done"

What gets logged:
- Deployment timestamp
- Commands executed
- Post-deploy verification
- Issues + resolution


## SPECIAL: HOTFIX FLOW
Bypasses Stages 1-5 for production emergencies.

Flow: Tech creates issue (label: hotfix) → AI Development →
      Code Review → Production → THEN retroactive PRD/FRD docs

Rules:
- Only for production bugs / security issues
- Tech creates + owns the issue
- AI builds fix immediately
- Minimal review, fast deploy
- AI creates retroactive documentation AFTER fix is live

# ============================================================
# CONFLICT RESOLUTION PROTOCOL
# ============================================================

When Product and Tech disagree:

1. Tech comments disagreement on ticket with reasoning
2. Product responds with business justification
3. If unresolved → label "needs-discussion", schedule sync
4. Decision logged using DECISION-LOG-TEMPLATE.md
5. Domain determines final say:
   - Business logic / scope → Product wins
   - Technical feasibility / architecture → Tech wins
   - Cost / timeline → discussed, Tech advises, Product decides

All disagreements and resolutions logged on the ticket.

# GAP ANALYSIS (14 Identified Gaps)
# ============================================================

## Gap 1: Emergency Hotfix Flow [CRITICAL — Phase 1]

Problem: 11-stage pipeline can't handle 2am production bugs.
Solution: "🚨 Hotfix" column bypasses Stages 1-5.
  Tech creates issue (label: hotfix) → AI builds fix →
  Code Review → Production → Retroactive docs AFTER fix is live.

## Gap 2: Ticket Dependencies [CRITICAL — Phase 2]

Problem: Feature B depends on Feature A's API being deployed.
Solution: Execution Plan includes "Depends On" field.
  @ticket-manager blocks development if deps aren't met.
  AI comments: "Blocked: waiting for #201 to reach Staging"

## Gap 3: Multi-PR Coordination [HIGH — Phase 4]

Problem: 1 feature = BE PR + FE PR. Partial merge = broken deploy.
Solution: @ticket-manager tracks all PRs per ticket.
  Nothing moves to Staging until ALL PRs approved.
  Feature flags allow code deploy without feature enable.

## Gap 4: Conflict Resolution [HIGH — Phase 1]

Problem: Product and Tech disagree on approach.
Solution: Escalation protocol in kanban-workflow.md.
  Business logic → Product wins.
  Technical architecture → Tech wins.
  All disagreements logged on ticket.

## Gap 5: Stale Ticket Detection [MEDIUM — Phase 7]

Problem: Tickets rot in columns with no one noticing.
Solution: Daily scheduled agent checks ticket age.
  >2 days in Code Review → ping reviewer.
  >3 days anywhere → ping owner.
  >5 days → escalate to team lead.

## Gap 6: Security Review [HIGH — Phase 2]

Problem: Auth/payment/PII features need security review.
Solution: Label `security-review` auto-detected by AI
  or manually added. Security review happens between
  Stage 5 and 6. Non-sensitive tickets skip it.

## Gap 7: QA / E2E Testing [MEDIUM — Phase 6]

Problem: Who does systematic QA beyond AI tests + Product testing?
Solution: @staging-deployer runs E2E suite on staging.
  Reports results before Product reviews.
  Product gets: "All automated tests pass. Manually verify: [list]"

## Gap 8: Documentation Updates [MEDIUM — Phase 6]

Problem: API docs, changelog, user docs never get updated.
Solution: @doc-writer runs at Stage 8 alongside staging deploy.
  Auto-generates API reference, changelog, user docs.
  Product reviews in Stage 9.

## Gap 9: Feature Flags [HIGH — Phase 4]

Problem: Can't deploy without enabling. Can't A/B test. Can't quick-disable.
Solution: Added to stack.yml (provider config).
  @execution-planner includes flag definition.
  Build agents wrap features in flags.
  Production checklist includes flag enable step.
  Rollback = disable flag (instant).

## Gap 10: Rollback Plans [HIGH — Phase 6]

Problem: What if staging/production deploy breaks?
Solution: @staging-deployer generates BOTH deploy AND rollback.
  Every migration tested for reversibility.
  Feature flags = instant rollback.
  Production checklist always has rollback section.

## Gap 11: External Context (meeting-notes tools, Slack) [LOW — Phase 7+]

Problem: Decisions happen in meetings/Slack, not on GitHub.
Solution: Convention: post meeting summaries on tickets.
  Decision log format includes References field.
  Future: MCP connectors auto-post to tickets.

## Gap 12: Knowledge Accumulation [MEDIUM — Phase 6]

Problem: After 50 features, how to find past decisions?
Solution: Decision logs on tickets (searchable).
  @doc-writer creates ADRs for significant decisions.
  AI reads past decisions before making execution plans.

## Gap 13: Onboarding Guide [MEDIUM — Phase 1]

Problem: New team member doesn't know the pipeline.
Solution: README.md includes:
  - How the 12 columns work
  - What AI does vs what humans do
  - How to interact with AI on tickets
  - Common workflows

## Gap 14: Velocity Metrics [LOW — Phase 7+]

Problem: Is the pipeline working? Where are bottlenecks?
Solution: Future scheduled agent calculates:
  - Average time per column
  - Rework rate (Stage 9 → 10)
  - AI accuracy (how often code review has changes)
  - Weekly summary posted to metrics issue

# ============================================================
# THOUGHT PROCESS: WHY EACH STAGE EXISTS
# ============================================================

PRD (Wiki): AI generates first draft, Product edits directly.
Living document — grows with every feature. Not a task, not on
the board. Like a Confluence page. Version history = audit trail.

STAGE 1 (FRD): Product owns because FRD = scope decisions.
If AI writes FRD, AI decides scope. That's dangerous.
Product knows business priority and "v1 simplicity" judgment.
FRD links back to Wiki PRD for context.

STAGE 2 (Execution Plan): The bridge nobody builds. Translates
product language into engineering specifics. This is where 80%
of project delays happen — the gap between what Product wants
and what Tech builds. The execution plan closes it explicitly.

STAGE 3 (Tech Approval): Guardrails. Tech knows things AI can't
infer: "We tried microservices for this last year and it failed."
Institutional knowledge captured here.

STAGE 4 (AI Development): AI reads Wiki PRD + FRD + Exec Plan +
Tech DO's/DON'T's. Richest context any developer has ever had.
By the time AI writes code, ambiguity is near zero.

STAGE 5 (Code Review): Same person from Stage 3. They have
context. Random reviewer would re-read everything. Same person
= faster, better review.

STAGE 6 (Staging): Production checklist generated HERE, not at
deploy time. Gets reviewed by Product (Stage 7) and Tech
(Stage 9) before production. Catches checklist errors early.

STAGE 7 (Staging Review): 70% of features need rework. This
isn't failure — it's how products get built. The framework
embraces it.

STAGE 8 (Rework): AI assesses scope first. "Move button left"
≠ "add offline support." Prevents scope creep through the loop.

STAGE 9 (Production): Human deploys. AI provides instructions.
Security, compliance, and "a human should be watching" are why.

# IMPLEMENTATION LIFECYCLE (Inside Stage 6)
# ============================================================

Contract-first development — FE can start in parallel with BE.

6.1  API CONTRACT FIRST (types, payloads, response shapes)
     ├── OpenAPI schema updated
     └── TypeScript types generated
          │
     ┌────┴────┐
     │         │
6.2  BE        6.3  FE (starts immediately, parallel)
     Models         API client from schema
     Real API       Components from Figma
     Tasks          Screens + state
     │              Uses mock/typed responses until BE ready
     │         │
     └────┬────┘
          │
6.4  Tests (both sides)
6.5  Update GitHub + PR
6.6  Deployment prep

WHY CONTRACT-FIRST:
- FE team doesn't wait for BE to finish
- API shapes are agreed upfront — fewer integration surprises
- TypeScript types generated from OpenAPI = compile-time safety
- Mock responses use real types, so FE code works when BE ships
